01  PROJECT CONTEXT
Introduction and Problem Statement
This project proposes a database backed application that controls access to protected resources and records each decision. A requester can ask to perform an action, while administrators maintain users, roles and permissions. Auditors inspect an ordered record of access decisions and policy changes. The course focus is the relational model, integrity constraints, transactions and queries that make those functions dependable.
Problem Statement
Small applications often scatter permission checks throughout their code. As roles change, inconsistent rules can allow an action in one screen and deny it in another. Logging may record only successful actions or omit the policy state that led to a denial. Investigators then cannot answer who attempted an action, when it happened and why the system allowed or denied it.
Objectives
Represent users, roles, resources and permissions with normalized relational tables and enforce referential integrity.
Evaluate a request against a clear default deny policy and persist the decision with its actor, action, resource and timestamp.
Allow authorized administrators to assign and revoke roles while recording each change as an audit event.
Provide searchable audit reports and demonstrate useful SQL joins, aggregates, constraints and indexes.
Scope and Assumptions
The prototype manages application level access to a set of registered resource types, such as documents and reports. It does not intercept arbitrary SQL issued outside the application. An administrator configures roles; an auditor has read access to audit history; an ordinary user requests protected actions. Test records are synthetic. Deletion of audit history is excluded from the application interface.
02  FUNCTIONAL DESIGN
Proposed Solution and Features
A central authorization service accepts actor, action and resource identifiers. It verifies an active account, finds active role assignments, joins those roles to permissions and returns allow only when at least one matching permission exists. Every completed evaluation writes an access decision event. Administrative changes use controlled screens that write the assignment and its audit record in one database transaction.
Features
Role
Supported actions
User
Sign in; inspect own role summary; request read, create, update or delete actions on registered resources; review own recent decisions.
Administrator
Create or deactivate users; maintain roles and permission mappings; assign or revoke a user role; register resources.
Auditor
Filter events by actor, action, decision, resource and time window; inspect policy change history; export a limited CSV report.

Key Business Rules
An inactive user or resource is denied before permission lookup. A missing permission is denied by default.
A user can hold multiple roles; duplicate user to role and role to permission pairs are forbidden by composite keys.
Only an administrator can change assignments, and an auditor cannot edit them. The last active administrator cannot remove their own final administrator role.
Each event stores a decision and a reason code such as NO_MATCHING_PERMISSION, INACTIVE_ACCOUNT or ALLOWED_BY_ROLE. The event also captures the request correlation ID.
Representative Use Case
An analyst asks to read report R42. The service checks account and resource status, joins the analyst’s roles to READ_REPORT permission, returns the decision, and writes an audit event with the matching role identifier or denial reason. The UI shows a short result without exposing internal policy tables.
03  COMPONENT VIEW
System Architecture and Workflow
The browser uses a server API. Authentication establishes the actor identity, while authorization applies the role mapping stored in PostgreSQL. The audit writer is part of the server process in the proposed prototype; the separate box shows a distinct responsibility, not a separate network service.

Figure 1  Proposed access control architecture
Request Sequence
Client sends a protected action with a resource identifier and request ID.
API authenticates the session and validates the resource and action.
Authorization service queries active assignments and matching permissions.
The decision event is inserted; the API returns allow or deny and displays a safe reason.
A role update uses a transaction: check administrator authority, update the junction table, append a policy change event and commit. If the audit insert fails, the role update rolls back. Authorization attempts are also recorded, including denials, with a conservative error response if durable logging is unavailable.
04  DATABASE DESIGN
Relational Data Model

Figure 2  Core entity relationships and keys
The model uses junction tables for the two many to many relationships. A separate RESOURCE table stores resource_id, resource_type, resource_key, owner_user_id and status. AUDIT_EVENT refers to an actor where known and stores action, resource reference, decision, reason_code, matching_role_id, request_id and occurred_at. A POLICY_CHANGE table records the administrator, target mapping, operation and time.
Integrity and Index Design
USER.email, ROLE.name and RESOURCE(resource_type, resource_key) are unique; foreign keys reject orphaned assignments.
Unique pairs on USER_ROLE(user_id, role_id) and ROLE_PERMISSION(role_id, permission_id) prevent accidental duplicates.
A unique permission pair (action, resource_type) defines the supported action vocabulary.
Indexes on AUDIT_EVENT(occurred_at), (actor_user_id, occurred_at) and (decision, occurred_at) support chronological filters.
The audit event stores a snapshot of the outcome and reason because later role changes must not alter the historical interpretation of an earlier decision. Audit and policy history are retained in append only application paths; privileged database administration remains outside that guarantee.
05  QUERY AND CONTROL DESIGN
Security Controls and Database Operations
Access Evaluation
The core query joins USER_ROLE to ROLE_PERMISSION and PERMISSION, filters active assignments and role status, and searches for the requested action and resource type. The service selects one deterministic matching role for its reason record. A denied lookup returns NO_MATCHING_PERMISSION. Resource ownership can be added as a later policy dimension, but the first release uses role permissions alone.
Audit and Administrative Controls
Control
Database implementation
Least privilege
Dedicated application account with only required table rights; auditor interface restricted to report queries.
Password handling
Store salted password hashes through a maintained authentication library; never store plaintext passwords or secrets in audit records.
History
No UPDATE or DELETE routes for audit tables in the application; immutable event identifiers and server generated timestamps.
Input safety
Parameterized SQL through the ORM or driver; allowlisted sort columns and bounded pagination.
Review
Reports for repeated denials, assignment changes by administrator and access to a chosen resource.

Example Course Queries
List users with effective permissions by joining users, assignments, roles and permissions.
Count allowed and denied requests by day and resource type with GROUP BY.
Find role changes followed by access to a resource within a selected time window.
Compare a user’s current role set with earlier decision snapshots.
An auditor may export filtered results after selecting a bounded date range. The export omits password hashes and session tokens. Database backups and the audit table access policy are administrative operations documented for the demonstration.

Acceptance Criteria
An authorized user can perform a permitted action; a missing permission and inactive account are denied.
Every attempted decision has one searchable event with request ID, time, outcome and reason.
A failed audit insert rolls back an administrative role change.
The schema rejects duplicate assignments and orphaned foreign keys; report filters return correct test data.
Risks and Deliverables
Primary risks are ambiguous resource naming, accidental administrator lockout and unbounded audit growth. Stable resource keys, a protected last administrator rule and indexed date range queries address those risks. Deliverables are the ER diagram, SQL schema and seed scripts, source code, test report and a short live demonstration.
